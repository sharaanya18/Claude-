# U11 — Execution order of activities in hand-drawn process diagrams (user-supplied, verbatim; Domain: Computer Vision, Medium, A10G)

## Overview
Each test item is a photo or scan of a business process diagram drawn by hand on paper, plus the list of activities written in it. For every pair of activities, predict how the two relate when the drawn process runs: one always comes before the other, they can happen in either order, or they never both happen in the same run.
Diagrams use BPMN: rounded boxes are activities. Circles are events: thin for start, thick for end, double for waiting on something such as a message or a timer. Diamonds are gateways: X or blank = choose one branch, + = run all branches at once. Solid arrows give the order of steps. Large rectangles (pools) separate organisations, dashed arrows between pools are messages. Students drew these while modelling scenarios (insurance claims, hospital reviews, course enrolment, order handling). The drawings are messy: arrows cross, curve and touch the wrong shape, text runs over lines, and some diagrams contain modelling mistakes. The answers describe what each drawing literally says, mistakes included.
The answers were not labelled by hand. Each drawing was turned into a model, and the model was executed with the rules in Execution rules. A solver that reads the diagram correctly can reproduce every answer exactly. The difficulty is reading the diagram: a few misread arrows change many pair relations. Test drawings come from modelling scenarios that never appear in training.

## Dataset
images/ (618 JPEG drawings, longer side at most 2000 px); train.csv (462 training drawings: id, image, activities JSON, relations); test.csv (156 test drawings: id, image, activities); train_diagrams.jsonl (for each training drawing the full diagram: every shape with its type and box, every arrow, pools, lanes and handwritten word boxes); sample_submission.csv (random relations).
activities: JSON list, one object per activity sorted by key: key (one capital letter A, B, C..., assigned in random order, not by position) and name (text written in the activity box as transcribed by a human, spelling mistakes included). Drawings have 3-14 activities (train mean 5.5, test mean 7.0). Names are distinct within a drawing ignoring case. Activities are rounded boxes including subprocesses (+ at bottom) or loops; events and gateways are not activities even when they carry text.
relations: space-separated tokens X-Y:relation, one per unordered pair of activity keys (X before Y in the alphabet): before (X can be followed by Y, never Y followed by X), after (Y always first), either_order (some runs X before Y and some Y before X, because of parallel branches, separate pools or loops), exclusive (no run contains both: alternative branches, or one can never run; drawings with at least half of the activities never running are not included). Relation counts in train: after 2,085, before 1,827, either_order 1,317, exclusive 1,061. Test has 3,608 pairs.
train_diagrams.jsonl line per training drawing: id, image_width, image_height, pools[] (id, name, collapsed, bbox), lanes[] (id, name, pool, bbox), nodes[] sorted left to right (id, type in task/subProcess/callActivity/startEvent/endEvent/intermediateCatchEvent/intermediateThrowEvent/exclusiveGateway/parallelGateway/eventBasedGateway, event message/timer/terminate/null, marker loop/multi_instance/null, name, activity key or null, pool, lane, bbox [x_min,y_min,x_max,y_max] in image pixels), sequence_flows[] (source,target node ids), message_flows[] (source,target node ids or pool ids), words[] (every handwritten word: text, angle, bbox). Ids local to each drawing. Training set holds 2,438 tasks, 796 exclusive, 576 parallel and 133 event-based gateways, 6,207 sequence flows, 794 message flows and 17,415 word boxes. Running the rules below on a training diagram gives exactly the relations in train.csv for all 462 drawings.

## Execution rules (token game; runs explore every possible choice)
1. Activities are nodes of type task, subProcess, callActivity; only activity firings count. Loop and multi-instance markers ignored (one step).
2. Tokens travel along sequence flows. When a node fires it consumes its input and puts tokens on its outgoing flows.
3. Input: a parallel gateway fires when every incoming flow holds a token and consumes one from each. Any other node fires on a token from any single incoming flow.
4. Output: an exclusive or event-based gateway puts a token on exactly one outgoing flow of its choice. Any other node puts a token on every outgoing flow.
5. Start: at the beginning every start event is triggered once; so is every other node with no incoming sequence flow. A triggered node fires once.
6. Messages: when a node with outgoing message flows fires it posts one message on each; exception: for exclusive/event-based gateways each outgoing message flow is one more alternative branch alongside its sequence flows. A node that receives a message flow from another node cannot fire until a message is waiting on one of its incoming message flows and consumes it when it fires. Message flows that start at a collapsed pool never block.
7. Terminate: a terminate end event removes every token of its own pool (or of the whole drawing if no pools). Messages already posted stay.
8. Cap: at most 2 tokens kept on a flow or message; extras discarded.
X > Y when some run fires X and fires Y at some later point. For X-Y: before if X>Y and not Y>X; after if Y>X and not X>Y; either_order if both; exclusive if neither. (Rules 5 and 6 follow what students meant rather than strict BPMN: plain arrows between pools are recorded as message flows; activities with no incoming arrow mean "when this message arrives".)

## Submission
CSV exactly id,relations, one row per test id; relations = space-separated X-Y:relation tokens, one per activity pair (n(n-1)/2). Pairs may be written in either order (B-A:before read as A-B:after). Tokens with unknown key/relation or self-pair ignored; first token counts if a pair repeats.
Evaluation: all 3,608 test pairs pooled; macro-averaged F1 over the four relations (before, after, either_order, exclusive). Random about 0.25; all-before about 0.12. A missing/unreadable pair is a false negative for its true relation and not a false positive. Whole submission rejected if columns are not exactly id,relations, row count differs, or any id missing/duplicated/unknown.

## What not to use
Training must happen in your solution (train or fine-tune a model inside the submitted code). General-purpose pretrained weights allowed (ImageNet backbones, general OCR or handwriting recognition models, general vision-language backbones); not weights fine-tuned on hand-drawn diagrams or flowcharts elsewhere. Implementing the execution rules is allowed (code that turns a recognised diagram into relations is part of a normal solution). Only the provided data; no other copies of these drawings or annotations, no other diagram datasets or external datasets. No test-set adaptation: predict each test drawing independently; no pseudo-labelling, test-time training, or tuning on the test set as a whole. No lookups or manual work: no reverse image search on test images, no matching against source archives, no hand labelling of test drawings, no hard-coded ids/answers, no hosted AI APIs.
Compute: A10G.
