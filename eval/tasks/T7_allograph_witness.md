# Task T7 — Allograph witness retrieval (paraphrased from the user's own challenge notes)

Each case is one rendered "board" image (JPEG, 1280x760 in practice although the spec says 1700x1100): 5 query panels (rubbing/facsimile character images, each with a coloured border and a small label tag in a corner) in the top band and 20 candidate crops (2 rows x 10, grey border, label box in a corner, often letterboxed with white padding) below. Candidates are labelled A-T. For each of the 5 queries, choose 2 candidate letters that are witnesses of the same character class; the 10 chosen letters across the board are distinct. Also predict a preference vector of 5 values in {0,1,2} (class mix about 17% / 41% / 42%).
Submission: `case_id, witness_pair_program, preference_vector`; program format `Q0:XY>Q1:XY>...>Q4:XY` (letters A-T, X<Y), vector as JSON `[a,b,c,d,e]`.
Metric: 0.65*PairProgramScore + 0.20*PreferenceScore + 0.15*JointCertificateScore; pair_i = 0.25*O (witness-letter overlap) + 0.30*P (exact query pairs) + 0.45*E (whole program exact); preference_i = 0.25*A (entry accuracy) + 0.75*V (whole vector exact); joint = both exact.
Data: 2,000 train boards, 500 test boards. The released preference rule is described by a distance formula but cannot be reproduced exactly from the rendered crops (labels were computed on original crops before rendering).
Rules: GPU-oriented fine-tuning (A10G); no inference from case_id, row order, file paths, JPEG size/compression or candidate-position frequencies; no thresholds, prototypes, normalisation statistics, pseudo-labels, clusters or parameters fitted on evaluation boards; no propagating inferred character identities across evaluation cases or building an eval-only character dictionary; validation must hold out complete character classes AND artifacts. Source crops recur across many boards within a split (hundreds of thousands of near-duplicate pairs in train), while all evaluation character classes are unseen.
