# CHALLENGE CONTRACT — assembly_amendments

**Name / domain family / difficulty**: French National Assembly amendment fate + joint-discussion grouping. Domain family: structured assignment / partition over a bag (per `eris-playbook` families: closest to "structured assignment" + "partition/bags", with a strong NLP (French legal text) feature-extraction component feeding both sub-tasks). Not a pure NLP classification task because the per-board constraint (exact fate counts, partition structure) dominates the output grammar.

**Decision unit**: one **board** (= one row of test.csv / one article-of-a-bill-in-one-body) is the unit the metric scores. Within a board, the **items** (amendments, `item_no` 1..n_amendments) are predicted jointly: `fates` is a permutation-constrained assignment (must match the board's `counts` exactly) and `joint` is a partition of the item indices. Across boards, prediction is independent (no information may flow between boards or between train/test boards except through a model fit on train).

**One valid answer**: for a test board with `n_amendments = n` and `counts = [a,r,f,w,m]` (summing to n):
- `fates`: JSON list of length n, values in {0,1,2,3,4}, in `item_no` order, using code 0 exactly `a` times, 1 exactly `r` times, 2 exactly `f` times, 3 exactly `w` times, 4 exactly `m` times.
- `joint`: JSON list of length n, integer group labels in `item_no` order; only the partition induced by equal labels matters (label values themselves are free, don't need to be contiguous or start at 0).

**Invalid answers (scored below zero / -1 on the relevant terms)**:
- `fates` wrong length, unparseable, or any code used a different number of times than `counts` → `carried` AND `disposal` both forced to -1 for that board.
- `joint` wrong length or unparseable → `joint` term scored 0 for that board (not -1 — re-read: "A list of the wrong length or one that cannot be read scores 0", vs the fates case which is explicitly -1; this asymmetry must be preserved in `metric.py`).
- Submission schema wrong (columns/order/row count/ids) → platform-level reject before scoring even starts (CSV Score Validation check), not merely a scoring penalty.

**Metric** (per board, then averaged with floor -1 per term, final mean of boards *100, floored at 0):
- `carried` (weight 0.35): binary adopted-vs-not on all n items. Chance-corrected: `(earned - expected)/(1 - expected)` where `expected` is the hit rate of a uniformly random permutation respecting the board's `a` (adopted) / `n-a` (not-adopted) split, i.e. `expected = a/n * a/n + (1-a/n)*(1-a/n)`... actually needs exact hypergeometric expectation — must derive and implement precisely in `metric.py`, not guess. **Skipped (not just zero-scored but excluded from the board's weighted mean) when `a == 0`** (no adopted amendment on the board).
- `disposal` (weight 0.35): among the amendments NOT adopted (n-a of them), 4-way classification (rejected/fell/withdrawn/not-moved) scored only on that subset; placing a non-adopted item as "adopted" (code 0) in the fates list, or any prediction, is wrong for this term if it's not the true one of the 4 — chance-corrected the same hypergeometric way against the board's [r,f,w,m] distribution among the n-a non-adopted items. Always defined when n-a>0 (true whenever a<n; if a==n i.e. all adopted, there is nothing to score and term is presumably undefined/skipped — confirm empirically, none observed with counts[1:]==[0,0,0,0] in a quick scan but must handle in metric.py).
- `joint` (weight 0.30): Adjusted Rand Index between predicted partition and true partition over the n items. **Skipped when the true partition has no pair sharing a label** (227/622 test boards, i.e., every amendment in its own singleton group — ARI is undefined/degenerate there since both ARI(singletons, anything)=0 trivially and the term says these aren't scored, so exclude from the weighted mean rather than counting as a guaranteed free 0... actually re-read: "Boards where no two amendments were called together ... are not scored on this term" = excluded from denominator, consistent with `carried`'s a==0 exclusion).
- Board score = weighted mean over the terms *that are defined for that board*, each floored at -1 before averaging (confirm floor applies per-term before the weighted mean, per "each floored at -1"). Final = `100 * mean_over_boards(board_score)`, floored at 0 at the very end (not per board).
- This is a genuinely non-standard metric: **must implement in `metric.py` with hand-computed extreme-case tests** (chance baseline exactly 0, perfect answer exactly weight-sum, wrong-length answer exactly -1, a==0 board excluded, singleton-only board excluded from joint term) before any modelling, per `eris-metric-engineer`.

**Submission**: `submission.csv`, columns exactly `item_id,fates,joint` in that order, one row per test board (622 rows), `item_id` matching `test.csv`'s ids (order from `sample_submission.csv`, which is already in test.csv's row order — confirmed by construction, verify in data audit). Cell grammar: `fates` and `joint` are **JSON-list-shaped strings inside a CSV field** (quoted since they contain commas), e.g. `"[1,2,0,1,4]"`. Reload with `pd.read_csv(..., keep_default_na=False)` and `json.loads` each cell to validate — not literal Python list objects.

**Data files**:
- `train.csv` (4392 rows) / `test.csv` (622 rows): board-level metadata — `item_id, bill_id, bill_title, bill_kind, reading, text_examined, examining_body, division, n_amendments, counts`. `counts` is a JSON-string `[adopted,rejected,fell,withdrawn,not_moved]` summing to `n_amendments`. `bill_id` is the group key for the hidden split (bills, not boards, are disjoint between train/test — confirmed: 0 overlap in `bill_id` between train.csv and test.csv in the sample we hold).
- `train_items.csv` (31566 rows) / `test_items.csv` (8851 rows): item-level — `item_id` (FK to board), `item_no` (1..n_amendments, **shuffled/renumbered, carries no order information**), `dispositif` (legal edit text, French, can be long/multi-paragraph), `expose` (summary text, French, or the literal placeholder string `"(pas d'exposé sommaire)"` when absent — must be treated as a missing-value sentinel, not real content, during feature engineering).
- `train_targets.csv` (4392 rows): `item_id, fates, joint` — ground truth in submission layout, used ONLY for training/CV (never has a test counterpart; this is the full supervisory signal).
- `sample_submission.csv` (622 rows): placeholder `item_id, fates, joint` with `fates=[]` and `joint=[]`-shaped-but-actually-empty strings — structurally valid but empty; defines the exact id column, order, and header the real submission must match. (Note: empty `[]` doesn't match `n_amendments>0` boards' expected length — confirms it's a "claims nothing" placeholder, not a schema template to copy literally; still use its `item_id` column/order as ground truth for row order and id set.)

**Hidden split**: bills (`bill_id`), not boards, are the split unit — confirmed 0 bill_id overlap between train and test in our own files, and the description states committee + plenary + every reading of the same bill stay together. CV must use **GroupKFold on `bill_id`**, never a random row/board split (an un-grouped split would leak: boards from the same bill/dossier share vocabulary, drafting style, political context, and even near-duplicate dispositif text across readings). Test is further divided into two unnamed "evaluation slices by bill" — unknown boundary; treat as another reason to keep CV strictly bill-grouped and to check for subgroup-level variance (e.g. by `bill_kind` or `examining_body`) since the private/public LB slicing may correlate with one of those.

**Compute / runtime**: not stated explicitly in the challenge text; CLAUDE.md default applies — target ≤ 50 min on one A10G, plan for ≤ 1 h worst case, ≥30% headroom. No challenge-specific override seen (no "CPU-only", no shorter stated limit). 31.5k + 8.9k short-to-medium French legal/text amendments is comfortably fine-tunable within budget for a moderate transformer (e.g. CamemBERT/FlauBERT-base or multilingual DeBERTa) at this scale.

**Allowed / required methods**: Not labelled "from-scratch" or restricted to a model family in the challenge text → CLAUDE.md §2.2/§6.2 defaults apply: pretrained HF backbone (French: CamemBERT, FlauBERT, or multilingual DeBERTa-v3) fine-tuned on `dispositif`+`expose`, feeding both the fate classification head and pairwise/clustering features for `joint`. GBDT on hand/learned features is fine as an ensemble member, not as the sole model (strip-test: must not reduce to a rule engine). TTA is not obviously applicable here (no natural "views" of a legal text) — skip rather than force it.

**Explicit bans (verbatim from "What not to use")**:
> "Do not use any external copy of these amendments, of their outcomes, of the records or reports of the sittings, or any model trained on them, and do not look up the withheld authors or outcomes. The task is to learn the fates and the grouping from the training boards provided."
This directly forbids: scraping/looking up Assemblée Nationale records (assemblee-nationale.fr dossiers, legifrance, compte-rendus) to reconstruct withheld author/outcome/order fields, using any externally pretrained model specifically trained on these legislative records (a generic French LM pretrained on web text/Wikipedia is fine; a model someone fine-tuned on AN amendment outcomes would not be), and any lookup of the real-world fate of a specific amendment. Also binds CLAUDE.md §2.3 #3 (no external datasets) and #5 (no test-set statistics beyond per-row inference).

**Silences and assumptions**:
- The metric prose for `carried`/`disposal` describes a hypergeometric chance-correction verbally; exact formula must be derived/tested, not assumed from a template — flag to `eris-metric-engineer`.
- Whether the floor of -1 applies before or after weighting per term, and whether a board with ALL terms undefined (a==n_amendments AND singleton-only AND ... ) can occur, needs checking empirically in the data audit (did not observe a==n in a first pass; must confirm in full audit).
- "Only which amendments share a label matters" — our predicted label *values* are free; ARI computation must be on the induced partition, not label identity (standard `sklearn.metrics.adjusted_rand_score` already satisfies this).
- `item_no` is described as "in a random order" for both train_items and test_items — i.e. it carries zero signal about tabling order; must not be used as a feature (the leakage-controls section explicitly withholds tabling order). Any model relying on `item_no` ordinal value would be fitting noise/overfitting to an artifact, and more importantly the row order in the *items* file is **not** guaranteed to match ascending `item_no` — must explicitly sort/index by `item_no` before building per-board sequences, and verify this empirically in the data audit.
- `expose == "(pas d'exposé sommaire)"` is a sentinel for "no summary" — treat as missing, not as literal text content, in any text-length or vocabulary feature engineering, and probably still fine to feed through a transformer tokenizer as literal missing-marker text (grey: harmless since it's a copied template string, not a leak).

**Per-row independence**: Explicitly NOT per-row independent *within* a board — the whole point of the `joint` grouping and the cascading "falls when the group's winner is adopted" mechanic is that fates of items in the same board are coupled. This coupling must be modelled (e.g. the joint partition predicted first/jointly, then fates predicted conditional on the partition and board-level counts) — a per-item-independent classifier ignoring the partition structure will systematically mis-predict `fell`. HOWEVER, **across boards** the usual CLAUDE.md §2.3 #5 rule holds absolutely: no pooling/statistics/clustering across different boards' items, and never using any test-set information (other than one board's own items, fit once at inference, zero-shot from the trained model) to fit transformers/encoders/thresholds. Within-board joint reasoning over that board's own items at inference time is normal per-sample (per-board) inference, not test-set fitting — this is analogous to a slate/listwise ranking model scoring one query's candidates together, which the challenge's own setup requires.

**Boilerplate to ignore**: None of the usual "no internet" / "rule-based is fine" boilerplate contradicts the guidebook here — HF pretrained French LM weights remain allowed per CLAUDE.md §1/§2.2, and a rule-only solution would fail the strip-test and the "What not to use" ML-training requirement implicit in CLAUDE.md §2.1 even though this challenge's own text doesn't explicitly demand "fine-tune a transformer" — the prime directive (§2.1) still applies: the model must do the learning, so a hand-built regex/lookup pipeline for fates or joint grouping is non-compliant even if it scored well, and must not be the shipped approach (it may be used as a diagnostic-only EDA step to understand the structure, never in `solution.py`).

**Description-vs-formula discrepancies / reviewer questions** (flag, do not guess):
1. Exact hypergeometric "expected" formula for `carried`/`disposal` chance-correction — derive mathematically in `metric.py`, cross-check against random-baseline Monte Carlo.
2. Whether `-1` floor is applied to the *term* before weighting or to the *board score* after weighting — re-read suggests per-term ("each floored at -1" appears right after describing the malformed-fates case, which is a term-level event) — implement per-term floor, verified against the "wrong length" sentence which explicitly says "this term and the next are -1" (term-level, confirmed, not board-level).
3. Confirm empirically: can `a==0` and `counts[1:]==[0,0,0,0]` (nothing but adopted) ever co-occur — would leave a board with zero definable terms; metric.py must not divide by zero / must handle this board-score-undefined case (likely: exclude the whole board from the final mean, matching "boards ... are not scored on this term" pattern, but the overview says every board has ≥1 scorable amendment so probably moot for `disposal`; test boards are stated to have "at least two different fates" which guarantees both carried-relevant terms are non-trivial but does NOT guarantee `a>0` nor a non-singleton joint).

**Biggest risk (single most important thing to get right)**: the **joint-discussion partition** is the structural backbone the other two terms causally depend on (a `fell` fate is *defined* as "an earlier decision in the same joint discussion already settled the passage") — if `joint` prediction is weak, `disposal`'s `fell` vs `rejected`/`withdrawn`/`not-moved` distinction will also be weak, dragging down 0.65 of the score indirectely even though `joint` itself is only weighted 0.30. The modelling plan must treat `joint` grouping as a first-class, early-pipeline problem (pairwise "same joint discussion" classifier over item pairs within a board, clustered into a partition), not an afterthought bolted onto a fate classifier. Second risk: GroupKFold on `bill_id` is mandatory — any leakage here would badly overstate CV vs the private LB, which splits on the same unit.
